1. End-to-End AX Engineering Loop

What is Arize AX? An AI engineering platform for observing, evaluating, and improving AI applications and agents. Engineers instrument applications to send traces into AX, inspect traces, spans, and sessions to understand behavior, apply evaluations to identify quality or agent failures, turn representative cases into datasets, experiment with prompts, models, retrieval, or agent configurations, and measure whether changes improve performance before and after deployment.

🔄 The Engineering Loop

Production AI App → Observe → Evaluate → Diagnose → Experiment → Measure → Ship ↑ | └────────────── Continuous production feedback loop ──────────────────┘

AX is not just a trace viewer. It supports a continuous improvement loop: observe production behavior, evaluate quality, diagnose failures, test changes, measure them, ship the improvement, and observe again.

Document AX around the user workflow, not only around screens: instrument → observe → diagnose → evaluate → build a dataset → experiment → compare → deploy → monitor.

2. Projects

Projects are the top-level organizational unit. All traces, evaluations, datasets, and experiments live inside a project. Separating applications or environments into different projects keeps telemetry isolated and organized.

Teams typically create one project per application or environment (e.g., support-agent-prod, support-agent-staging).

3. Tracing: Traces & Spans

📊 Trace & Span Hierarchy

TRACE: One End-to-End Request SPAN: Agent → SPAN: Retriever → SPAN: LLM → SPAN: Tool Call Inspect inputs, outputs, latency, tokens, attributes, status, and evaluations at each step. Trace = complete story. Span = one operation inside the story.

Traces

A trace represents one complete end-to-end request through an AI application. When a user asks a question and the system retrieves context, calls a model, and returns an answer, the entire sequence is one trace.

Spans

Spans are the individual operations inside a trace: agent logic, retrieval, model calls, tools, embeddings, or other instrumented work. Each span records:

  • Inputs & outputs — what went in, what came out
  • Timing — start time, duration, latency
  • Status — OK, ERROR, with error messages
  • Token usage — prompt tokens, completion tokens, total
  • Attributes — structured metadata (model name, temperature, etc.)
  • Evaluations — quality scores attached at the span level
Use case: The final answer is wrong. Instead of guessing that the model failed, the engineer opens the trace and discovers that the retriever span returned irrelevant documents. The actual root cause is retrieval, not generation.
A trace tells me what happened end to end; spans tell me where it happened.

4. Evaluations

🎯 Evaluation Pipeline

User Input → AI Output → Evaluator (LLM / Code) → Correctness → Relevance → Groundedness → Tool Quality

Software can return HTTP 200 and still produce a bad AI answer. Evaluations measure semantic quality and behavior, not merely system uptime.

Evaluation Types

TypeMethodBest For
CorrectnessLLM-as-judgeIs the answer factually right?
RelevanceLLM-as-judgeDoes the answer address the question?
GroundednessLLM-as-judgeIs the answer supported by retrieved context?
HallucinationLLM-as-judge / codeDoes the answer contain fabricated information?
SafetyLLM-as-judge / codeDoes the output violate safety guidelines?
Tool SelectionDeterministicDid the agent pick the right tool?
Use case: A customer-service response is fast and error-free but states a 90-day return policy when the actual policy is 30 days. A correctness or groundedness evaluator flags the response even though the request technically succeeded.
Traditional observability asks "did the system run?" AI evaluation asks "did it behave well?"

5. Datasets

📁 Production Failure → Dataset → Experiment

Production Failure → Trace → Dataset → Experiment → Measured Improvement Turn real failures into repeatable regression tests.

Bad production traces are valuable test material. Instead of fixing one incident and forgetting it, teams preserve representative cases in datasets and use them to test future versions.

  • Capture failing traces as dataset rows
  • Include inputs, expected outputs, and context
  • Use datasets as regression tests for experiments
  • Build golden datasets for evaluation baselines
Use case: Twenty users trigger the same retrieval failure. Those cases become a dataset. The team tests a new retrieval strategy and evaluates whether it fixes those failures without degrading other cases.
AX helps connect production observability to development experimentation. That feedback loop is one of the strongest reasons to use an AI engineering platform.

6. Experiments

🧪 Prompt / Model Experiment Comparison

Test Dataset Baseline A Candidate B Correctness: 0.81 Correctness: 0.94 Hallucination: 8% Hallucination: 2% Latency: 1.2s Latency: 1.3s

AX experiments make changes measurable. A team can compare prompts, models, agent configurations, or other application variants against the same dataset and evaluation criteria.

Use case: A stricter system prompt improves groundedness but increases latency slightly. The experiment exposes the tradeoff so the team can make an engineering decision based on evidence rather than intuition.
Use case: Compare two model providers for quality, latency, and cost-sensitive token behavior before changing production routing.
Prompt engineering becomes an experiment with a baseline, candidate, dataset, metrics, and repeatable results.

7. Agents & Tool-Use Debugging

🤖 Agent Tool-Use Investigation

User → Agent → Select Tool → Tool Result → Reason / Continue → Answer Evaluate the path, not only the final answer. Tool selection · parameters · sequence · errors · convergence · final quality

Agent quality includes the route an agent takes, not just the text it eventually returns. Tool selection, arguments, ordering, repeated calls, failures, and convergence can all be inspected and evaluated.

Use case: An agent gives the correct weather answer but calls three unrelated tools first, wasting time and tokens. Final-answer evaluation may pass, while trajectory/tool-use evaluation exposes inefficiency.
Use case: An account-support agent chooses the correct lookup_account tool but passes the wrong customer identifier. Span-level inspection separates tool-selection quality from parameter-extraction quality.
Agent observability is about understanding both outcome and execution path.

8. Sessions

💬 Sessions & Production Monitoring

SESSION: One User Conversation PRODUCTION MONITORING Trace 1: Where is my order? Correctness 96% Trace 2: When will it arrive? Hallucination rate 2% Trace 3: Change delivery address? P99 latency 4.8s Tool failure rate 1% Dashboards + alerts surface trends and regressions.

Sessions group multiple traces from the same conversation or interaction sequence. This enables multi-turn analysis that single-trace inspection misses.

Use case: Every individual answer in a support conversation looks plausible, but the user repeatedly asks the same question because the agent never resolves the issue. Session-level evaluation reveals unresolved conversations or frustration that single-turn analysis misses.
AX supports multiple levels of analysis: span → trace → session → population-level monitoring.

9. Dashboards & Monitoring

Dashboards move from debugging one request to understanding system-wide behavior. Teams can track aggregate quality, latency, token usage, errors, evaluator results, and other production signals.

  • Aggregate quality tracking — correctness, relevance, groundedness over time
  • Latency monitoring — P50, P95, P99 across spans and traces
  • Token usage — cost analysis per model, per feature
  • Error rates — system errors vs. semantic quality failures
  • Alerting — surface regressions after deployments
Use case: A new deployment causes groundedness scores to fall and P99 latency to rise. Dashboards expose the trend; alerts surface the regression; engineers drill from aggregate metrics into representative traces and spans.
