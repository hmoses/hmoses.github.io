1
No Framework-Agnostic TypeScript Quickstart
TS Get-Started Page High Severity
📄 TS Quickstart → 📄 phoenix-otel SDK Ref →
⚠️ Issue

The TypeScript quickstart ONLY covers the Mastra framework path. If a developer uses Express, Fastify, Hono, or custom Node.js, there's no "raw OTLP + @arizeai/phoenix-otel" quickstart. The Python quickstart has auto_instrument=True for any framework, but TS has no equivalent generic path in the getting-started flow. The SDK reference page has the info — but it's not surfaced in the quickstart where devs land first.

✅ Proposed Fix

Add a "Framework-agnostic" tab to the TS quickstart showing raw register() + manual span creation with @arizeai/phoenix-otel. Mirror the Python quickstart's framework-agnostic approach.

💬 Talking Point
Your TS quickstart assumes Mastra. A dev using Hono or Fastify has to piece together the SDK reference page themselves. I'd add a framework-agnostic tab — just like your Python quickstart already handles any framework.
2
PROMPT.md Doesn't Cover Non-LLM Span Patterns
PROMPT.md (Agent Setup) Medium Severity
📄 PROMPT.md (Raw) → 📄 Agent-Assisted Setup →
⚠️ Issue

PROMPT.md is excellent for LLM call instrumentation — the routing table, phase 1/2 approach, and framework detection are well-designed. But it doesn't cover how to trace non-LLM operations: template selection, prompt assembly, data retrieval, custom business logic spans. Complex agents do far more than call LLMs — they orchestrate pipelines. I traced these exact patterns in my Phoenix Report (template selection → prompt assembly → provider dispatch) and this pattern isn't documented for agents to follow.

✅ Proposed Fix

Add a "Custom spans for non-LLM operations" section to PROMPT.md showing how to create CHAIN, TOOL, and RETRIEVER spans for business logic. Include the withSpan() helper from @arizeai/phoenix-otel.

💬 Talking Point
When I instrumented Poly-Glot, the hardest part was tracing non-LLM operations — template selection, prompt assembly. PROMPT.md doesn't cover that pattern, and it's exactly what complex agents need. I documented how I solved it in my Phoenix Report.

4
Node.js Protobuf OTLP Requirement — HTTP 415 Gotcha
TS Manual Setup Path High Severity
📄 TS Quickstart → 📄 Tracing FAQ → 📄 My Phoenix Report →
⚠️ Issue

Node.js requires @opentelemetry/exporter-trace-otlp-proto instead of the default HTTP JSON exporter — otherwise you get HTTP 415 errors with zero explanation. The quickstart uses @arizeai/phoenix-otel which handles this internally, but if anyone follows the manual OTel setup path (common for existing apps with OTel already configured), this gotcha isn't documented until you hit the error. I discovered and documented this in my Phoenix Report.

✅ Proposed Fix

Add a troubleshooting callout to the TS quickstart and the tracing FAQ: "Getting HTTP 415? You need the protobuf OTLP exporter (@opentelemetry/exporter-trace-otlp-proto), not the default HTTP JSON exporter."

💬 Talking Point
I hit the protobuf OTLP gotcha myself — HTTP 415 with zero explanation. I documented the fix in my Phoenix Report. That's exactly the kind of setup friction I'd eliminate on day one.
5
ESM Compatibility Not Documented for TypeScript
TS/JS Setup Docs Medium Severity
📄 TS Quickstart → 📄 phoenix-otel SDK Ref → 📄 My Phoenix Report →
⚠️ Issue

ESM (ES Modules) vs. CommonJS compatibility is a well-known pain point in the Node.js OpenTelemetry ecosystem. I had to pin specific package versions to get ESM working with Phoenix. The docs don't mention ESM at all — not in the quickstart, not in the SDK reference, not in troubleshooting. Every modern Node.js project using "type": "module" in package.json will hit this.

✅ Proposed Fix

Add an "ESM / CommonJS" section to the TS setup docs noting which packages need version pinning and what "type": "module" means for OTel initialization order.

💬 Talking Point
ESM compatibility with OpenTelemetry is a known pain point. Your docs don't mention it — I'd add a troubleshooting section because every Node.js dev using ESM will hit it.

Cookbooks Are Overwhelmingly Python — TS Parity Gap
Phoenix Cookbooks Medium Severity
📄 Cookbooks Index → 📄 TS Eval Cookbook (exists) → 📄 Agentic RAG (Python-only) →
⚠️ Issue

Of 20+ cookbooks listed in the Phoenix docs, only 2–3 are TypeScript. The vast majority are Python-only. Given the explosive growth of the TS/JS agent ecosystem — Mastra, Vercel AI SDK, LangChain.js, OpenAI Agents SDK (Node) — this is a significant coverage gap. Arize already supports these frameworks, but there's no cookbook showing a complete workflow.

✅ Proposed Fix

Create TypeScript versions of the top 5 most-visited Python cookbooks. Prioritize: Agentic RAG Tracing, Structured Data Extraction, and the Iterative Eval & Experimentation workflow (which already has a TS version — good precedent to follow).

💬 Talking Point
Your cookbook library is overwhelmingly Python. With Mastra, Vercel AI SDK, and LangChain.js growing fast, I'd prioritize TypeScript cookbook parity — starting with the top 5 most-visited recipes.
