Developer documentation / v1.0 / independent portfolio

Your first LanceDB query.

Install LanceDB Embedded, create a local table from known vectors, search by similarity, filter on metadata, and verify the behavior with automated tests.

Scope: This is a standalone educational lab. It uses synthetic, four-dimensional numeric embeddings—no external model, API key, cloud account, or real user data. The browser explorer is a simulation; the Python source executes actual LanceDB APIs.

1. Requirements

  • Python 3.11 or newer and pip.
  • A local working directory with the lab source files.
  • Network access for initial Python package installation; subsequent local queries need no external service.

From the lancedb-lab folder, create an isolated environment and install dependencies:

Terminal / setup
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
Understand this example: Set up your Python environment

python3 -m venv .venv creates an isolated Python environment so lab dependencies do not alter system packages. source .venv/bin/activate activates it on macOS/Linux. python -m pip install -r requirements.txt installs the packages listed in the project. On Windows, activate with .venv\Scripts\activate.

Windows PowerShell users can replace the activation command with .venv\Scripts\Activate.ps1. If a Python wheel is unavailable for your platform, use a supported CPython version and architecture.

2. Quickstart

Run your first query

Terminal / real LanceDB
python example.py --intent vector --limit 3
Understand this example: Execute the sample

python example.py starts the included runnable Python program. --intent vector selects the predefined query embedding for vector search, and --limit 3 requests at most three nearest records. The terminal prints IDs, titles, categories, and SDK-computed distances.

Expected behavior: the command creates a temporary local database, inserts eight predefined records, runs cosine vector search, prints up to three records ordered by ascending cosine distance, and automatically deletes the temporary directory afterward. The precise distance values are determined by the embedded SDK.

Inspect the core pattern

Python / connect → create → query
import lancedb
from example import RECORDS

db = lancedb.connect("./sample.lance")
table = db.create_table(
    "doc_chunks",
    data=RECORDS,
    mode="overwrite",
)
matches = (
    table.search([0.10, 0.99, 0.11, 0.15])
    .distance_type("cosine")
    .limit(3)
    .to_list()
)
for item in matches:
    print(item["title"], item["_distance"])
Understand this example: Connect, ingest, and retrieve

import lancedb imports the SDK. from example import RECORDS loads eight sample dictionaries with four-number vectors. connect creates/opens the local database; create_table writes rows, replacing the prior table because of mode='overwrite'. search starts nearest-neighbor retrieval, distance_type('cosine') selects cosine distance, limit caps matches, and to_list executes and materializes result dictionaries. The loop prints fields from each returned row, including its _distance. Lower cosine distance means a closer match.

The RECORDS fixture provides a vector column containing exactly four floating-point values per row. LanceDB can infer that this is the vector column. The _distance value is smaller for closer matches.

Important: mode="overwrite" replaces a table with the same name. It is appropriate here only because this project uses disposable example data. In a production workflow, use an intentional table-creation or migration strategy.

3. Query with filters

Metadata filters restrict which rows are eligible before the similarity search. You can experiment with the same behavior in the interactive result explorer.

Python / vector + metadata predicate
results = (
    table.search([0.16, 0.90, 0.19, 0.55])
    .distance_type("cosine")
    .where("category = 'search'")
    .limit(3)
    .to_list()
)
assert all(row["category"] == "search" for row in results)
Understand this example: Apply a metadata filter

table.search creates a vector query using a four-number query embedding. .where("category = 'search'") filters candidate rows by metadata, so rows in other categories are excluded. .limit(3) returns at most three results; .to_list() executes the query. assert all(...) is a simple correctness check: it fails if a returned row has another category. This example assumes the table variable from the preceding snippet.

The example's search_docs() function validates category names against a fixed allowlist. Do not concatenate arbitrary user input into filter expressions. For real applications, validate user-supplied fields and values and use parameterized predicates where supported by your SDK.

Try these commands and compare their returned categories:

Terminal / experiments
python example.py --intent filter --category search
python example.py --intent agent --category agents
python example.py --intent ingest --category python --limit 2
Understand this example: Compare command-line scenarios

Each command runs example.py with a different query intent and category filter. --intent chooses a sample embedding, --category restricts results to the specified metadata category, and --limit 2 returns up to two rows. These commands are reproducible comparisons, not generated text embeddings.

ConceptWhat this lab demonstrates
EmbeddingA fixed 4D numeric vector; not generated from text
DistanceCosine distance; a smaller _distance indicates a closer neighbor
FilterSQL-like where predicate on category metadata
IndexNo ANN index is needed for this tiny fixture; exhaustive search keeps results easy to inspect
Production pathReplace synthetic vectors with a real embedding pipeline; consider index strategy only after measuring workload

4. Automated validation

The test suite checks table construction, row count, deterministic search, category filtering, and invalid input. Tests run against a local temporary LanceDB database.

Terminal / pytest
python -m pytest -q tests
Understand this example: Run automated tests

python -m pytest -q tests invokes pytest with the Python interpreter in your active environment. tests is the directory of automated checks, while -q shows concise test output. A passing run means the currently installed dependencies satisfy the assertions; failures indicate a change to investigate.

Review the test source and the GitHub Actions workflow. Workflow results should be checked in the repository's Actions tab; the mere presence of a workflow file does not prove it has passed.

Documentation quality contract

  • Runnable: every code path has an explicitly declared dependency and no hidden API key.
  • Repeatable: sample inputs and expected output properties are stable.
  • Clear boundaries: browser simulation and real LanceDB executions are distinguished.
  • Change detection: tests should fail when an SDK change breaks documented behavior.
  • Agent-readable: prerequisites, commands, inputs, outputs, and verification steps are explicit.

5. Troubleshooting

SymptomLikely cause and action
ModuleNotFoundError: lancedbActivate the virtual environment and install requirements.
Dimension mismatchUse a query vector with exactly four elements to match this fixture.
No filtered matchesCheck that the metadata category exists; this lab's choices are python, search, agents, operations.
Unexpected result orderingConfirm the same query vector and cosine metric; lower distance means closer.
Permissions on local data pathUse a writable directory; the example's default temporary directory avoids most path errors.
Browser simulation differs from PythonCompare the fixed input vectors and metric; the browser is a teaching visualization, not the DB engine.
