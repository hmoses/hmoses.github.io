Understand this example: Read the system flow

The diagram traces two independent execution paths from the same illustrative four-dimensional records: the browser calculates cosine similarity directly in JavaScript, while Python creates a local LanceDB table and retrieves neighbors with the LanceDB SDK. These results demonstrate related retrieval concepts but are not identical execution engines. Metadata filtering narrows candidate records, and automated tests validate the Python path.

  1. Synthetic recordsEight deterministic records, four-dimensional vectors, and category metadata.
  2. Two execution pathsBrowser-side cosine simulation for learning, and real Python queries against LanceDB Embedded.
  3. Search and filterChoose an intent and category, rank by cosine distance, and inspect results.
  4. Linked documentationFollow runnable examples, architecture notes, and AI-agent task contracts.
  5. Automated validationpytest checks the real Python example; CI is configured, but its success must be verified separately.

The browser runs only static JavaScript. It is not a hosted database, does not fetch arbitrary documents, and makes no network calls to embedding providers. Real LanceDB queries execute through example.py on a developer machine or in CI.

2. Data contract

FieldTypePurpose
idStringStable record identifier
titleStringDeveloper-facing result title
textStringDescriptive content (not auto-embedded)
categoryStringFilterable metadata
vectorFour floatsIllustrative numeric embedding

Vector dimension is fixed at four for teaching. In a real system, all vectors in a column must match the embedding model's output dimensions and appropriate Arrow schema. Do not treat this lab's vectors as meaningful semantic embeddings extracted from the titles.

3. Execution boundaries

BROWSER

Educational visualization

Deterministic cosine similarity, local category filtering, scores, and Python example generation. No API key or server.

PYTHON

Actual LanceDB SDK

Embedded database, on-disk Arrow/Lance-backed storage, cosine queries, metadata predicates, and pytest verification.

Do not represent the browser demo as LanceDB compiled to WebAssembly or as a real Python kernel. Its purpose is conceptual understanding; the executable Python is the authoritative behavior demonstration.

4. Indexing and scaling

There is no approximate nearest-neighbor (ANN) index in this tiny example. An exhaustive query is appropriate for a handful of records and simplifies evaluation. Index selection for larger workloads involves dataset size, search latency, recall, vector dimension, and write patterns. An index's distance metric must align with the query metric.

Related official references: Vector search, Metadata filtering, and Vector indexing.

5. Quality gates

  1. Install dependencies in an isolated Python environment.
  2. Create a fresh local table from the fixed fixture.
  3. Check count, result limit, ranking properties, and the metadata filter contract.
  4. Reject unsupported intent names, categories, and limits.
  5. Run checks in GitHub Actions on changes under lancedb-lab/.

See test_example.py and the validation guide. This is one part of an engineering-oriented documentation strategy, not a benchmark or performance claim about LanceDB.
